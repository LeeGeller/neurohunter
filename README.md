# NeuroHunter

NeuroHunter — open-source сервис для персонализированного анализа вакансий.

Проект учитывает не только профессиональное соответствие кандидата вакансии, но и совместимость условий работы с профилем пользователя.

Основные параметры анализа:

* профессия, навыки и опыт;
* график и формат работы;
* коммуникация, встречи и звонки;
* многозадачность и переключение контекста;
* дедлайны и информационная нагрузка;
* автономность и стиль управления;
* размер команды и рабочая среда;
* командировки и физическая нагрузка;
* другие характеристики рабочего процесса.

Цель проекта — не просто найти подходящие вакансии, а определить, насколько сама работа соответствует конкретному пользователю.

Проект находится в активной разработке.

# Архитектура

```text
UserProfile
     │
     ▼
UserFeatures
     │
     ├── job_titles
     └── hard_constraints
             │
             ▼
        Search Tasks
             │
             ▼
          Go Parser
             │
             ▼
            Habr
             │
             ▼
          MongoDB
             │
             ▼
      Primary Filtering
             │
             ▼
      Vacancy Analysis
             │
             ▼
        Celery Worker
             │
             ▼
       Ollama / Qwen3
             │
             ▼
      VacancyFeatures
             │
             ▼
         PostgreSQL
             │
             ▼
       Matching Engine
```

Пользовательские данные и результаты анализа хранятся отдельно:

```text
User
├── UserProfile
├── UserFeatures
├── ResumeDocument
└── ResumeFeatures
```

Вакансии хранятся отдельно от их структурированного LLM-анализа.

# Основные компоненты

## Python Analyzer

Расположен в:

```text
services/analyzer/
```

Отвечает за:

* FastAPI;
* пользовательские данные;
* авторизацию;
* PostgreSQL;
* MongoDB;
* обработку резюме;
* LLM-анализ;
* Celery tasks.

---

## Go Parser

Go-сервис отвечает за сбор вакансий.

Текущий источник:

```text
Habr Career
```

Основные задачи:

* поиск вакансий;
* парсинг;
* формирование структуры `Vacancy`;
* сохранение в MongoDB;
* предотвращение дубликатов.

Основной endpoint:

```http
GET /search?query=<query>
```

Текущий поток:

```text
Search query
     │
     ▼
Go /search
     │
     ▼
Habr
     │
     ▼
MongoDB
```

---

## MongoDB

MongoDB используется для хранения исходных вакансий.

Это позволяет повторно анализировать уже собранные вакансии без повторного обращения к источнику.

---

## PostgreSQL

PostgreSQL используется для хранения:

* пользователей;
* `UserProfile`;
* `UserFeatures`;
* `ResumeDocument`;
* `ResumeFeatures`;
* будущих результатов анализа вакансий и matching.

---

## Ollama

Для локального LLM-анализа используется Ollama.

Основная модель:

```text
Qwen3:8B
```

LLM используется для преобразования неструктурированных данных в структурированные признаки:

```text
UserProfile    → UserFeatures
ResumeDocument → ResumeFeatures
Vacancy        → VacancyFeatures
```

---

## RabbitMQ и Celery

RabbitMQ используется как брокер сообщений.

Celery выполняет фоновые задачи, в том числе LLM-анализ.

Основной принцип:

```text
Celery Task
     │
     ▼
RabbitMQ
     │
     ▼
Celery Worker
     │
     ▼
LLM
     │
     ▼
Database
```

Сейчас Celery используется для анализа пользовательского профиля, резюме и запуска поиска вакансий.

# UserFeatures

`UserFeatures` — структурированное представление профиля пользователя, подготовленное для дальнейшей обработки.

```text
UserFeatures
├── job_titles
├── hard_constraints
├── preferences
├── tolerances
└── context
```

## job_titles

`job_titles` содержит варианты профессиональных названий, которые могут использоваться для поиска вакансий.

Они формируются на основе:

* профессии;
* опыта;
* специализации;
* технологий;
* профессионального направления.

Например:

```text
Python Backend Developer
Backend Developer
Python Developer
Django Developer
```

Одинаковые названия у разных пользователей в дальнейшем должны объединяться в один поисковый запрос.

## hard_constraints

Жёсткие ограничения пользователя.

Они должны использоваться для предварительного отбора вакансий до дорогостоящего LLM-анализа.

Примеры:

```text
- определённый формат работы;
- отсутствие ночных смен;
- отсутствие командировок;
- минимальный уровень оплаты.
```

## preferences

Предпочтительные характеристики работы.

Они учитываются при последующем matching, но не обязательно исключают вакансию.

## tolerances

Условия, которые пользователь способен принимать, даже если они не являются предпочтительными.

## context

Дополнительная информация для интерпретации пользовательского профиля.

# UserFeaturesExtractor

`UserFeaturesExtractor` преобразует `UserProfile` в `UserFeatures` с помощью LLM.

```text
UserProfile
     │
     ▼
USER_FEATURES_PROMPT
     │
     ▼
Ollama / Qwen3
     │
     ▼
JSON
     │
     ▼

     │
     ▼

```

Полученный результат валидируется перед сохранением.

# Поиск вакансий

Поиск вакансий запускается через Celery.

Текущая задача:

```text
search_vacancies(query)
```

Поток:

```text
Celery
  │
  ▼
Go /search
  │
  ▼
Habr
  │
  ▼
MongoDB
```

На текущем этапе задача принимает поисковый запрос напрямую.

Следующий этап — автоматическое формирование запросов из `UserFeatures.job_titles`.

Планируемый процесс:

```text
UserFeatures всех пользователей
          │
          ▼
      job_titles
          │
          ▼
    объединение списков
          │
          ▼
     удаление дублей
          │
          ▼
   уникальные запросы
          │
          ▼
        Habr
```

Это позволит не выполнять одинаковый поиск несколько раз для разных пользователей.

# Первичная фильтрация

После поиска вакансия должна проходить предварительный отбор до LLM-анализа.

Первичная фильтрация выполняется на основании структурированных данных вакансии и жёстких ограничений пользователя.

Примеры условий:

* зарплата;
* формат работы;
* место работы;
* опыт;
* тип занятости;
* график;
* другие явно заданные ограничения.

Для этого созданы отдельные компоненты:

```text
internal/
├── users/
└── filtering/
```

`users` предназначен для получения необходимых пользовательских данных.

`filtering` будет содержать логику предварительного отбора вакансий.

Полноценная реализация первичной фильтрации находится в разработке.

Планируемые группы признаков:

Основной источник этих признаков — LLM-анализ описания вакансии.

# Matching

После анализа пользователя, резюме и вакансии система должна выполнять matching.

```text
UserFeatures
     +
ResumeFeatures
     +
VacancyFeatures
     │
     ▼
Matching Engine
     │
     ▼
VacancyMatch
```

Matching должен учитывать:

### Профессиональное соответствие

* должность;
* опыт;
* навыки;
* технологии;
* проекты;
* требования вакансии.

### Совместимость с рабочей средой

* график;
* формат работы;
* коммуникацию;
* встречи;
* звонки;
* многозадачность;
* переключение контекста;
* информационную нагрузку;
* дедлайны;
* автономность;
* размер команды;
* стиль управления;
* рабочую среду;
* командировки.

### Пользовательские условия

* жёсткие ограничения;
* предпочтения;
* допустимые условия.

# Связь Vacancy и User

На этапе предварительного отбора одна вакансия потенциально может соответствовать нескольким пользователям.

Планируемая структура:

```text
Vacancy
├── User 1
├── User 7
└── User 15
```

Такая связь позволит после первичного отбора анализировать вакансию только относительно пользователей, для которых она прошла предварительную проверку.

На текущем этапе эта связь ещё не реализована.

# Авторизация

Используется JWT-аутентификация с подтверждением электронной почты.

Поддерживаются:

* регистрация;
* подтверждение email;
* Access token;
* Refresh token;
* Verification JWT;
* обновление Access token.

Access token используется в запросах:

```http
Authorization: Bearer <access_token>
```
