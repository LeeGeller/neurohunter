# NeuroHunter

NeuroHunter — сервис для персонализированного анализа вакансий.

Проект помогает ответить не только на вопрос:

> «Подхожу ли я этой вакансии?»

но и на вопрос:

> «Подходит ли эта работа мне?»

Основная идея NeuroHunter — разделять **профессиональное соответствие** и **совместимость с рабочей средой**.

Система должна учитывать не только профессию, навыки и опыт пользователя, но и особенности самой работы:

* график;
* продолжительность рабочего дня;
* формат работы;
* количество коммуникации;
* встречи и звонки;
* многозадачность;
* переключение контекста;
* уровень автономности;
* дедлайны;
* информационную нагрузку;
* прерывания;
* командировки;
* размер команды;
* рабочую среду;
* другие параметры, влияющие на комфорт и устойчивость работы.

Цель проекта — не просто показать результат подбора, а объяснить, **почему конкретная вакансия подходит или не подходит пользователю**.

Проект находится в активной разработке.

```text
ResumeDocument
    │
    ▼
PostgreSQL
    │
    ▼
Celery Task
    │
    ▼
RabbitMQ
    │
    ▼
Celery Worker
    │
    ▼
ResumeFeaturesExtractor
    │
    ▼
Ollama / Qwen3
    │
    ▼

    │
```

Celery-задачи получают идентификаторы объектов, а не передают через очередь большие объекты целиком.

Например:

```python
analyze_user_profile(user_id)
analyze_resume(user_id)
```

Worker самостоятельно загружает актуальные данные из PostgreSQL перед выполнением анализа.

Это позволяет избежать передачи больших структур через брокер и гарантирует работу с актуальным состоянием данных.

# Основные компоненты

## Go Parser

Go-сервис отвечает за сбор вакансий:

* получение вакансий из источников;
* парсинг данных;
* формирование исходной структуры вакансии;
* сохранение вакансий в MongoDB;
* предотвращение появления дубликатов.

Исходная вакансия сохраняется отдельно от результата LLM-анализа.

Это позволяет повторно обрабатывать уже собранные данные после:

* изменения промпта;
* смены модели;
* изменения структуры признаков;
* изменения логики анализа.

Повторно запускать парсер для этого не требуется.

---

## MongoDB

MongoDB используется для хранения исходных вакансий.

В базе сохраняется исходное содержимое вакансии до дальнейшего анализа.

Разделение исходных данных и результатов обработки позволяет:

* повторно анализировать вакансии;
* менять LLM;
* изменять промпты;
* изменять структуру `VacancyFeatures`;
* не выполнять повторный парсинг уже собранных вакансий.

---

## Python Analyzer

Python-анализатор находится в:

```text
services/analyzer/
```

Он отвечает за:

* API на FastAPI;
* работу с PostgreSQL;
* работу с MongoDB;
* авторизацию;
* пользовательские данные;
* обработку резюме;
* интеграцию с Ollama;
* LLM-анализ;
* извлечение структурированных признаков;
* фоновые задачи Celery;
* подготовку данных для последующего matching.

# Ollama и Qwen3

NeuroHunter использует локальный LLM через Ollama.

Основная модель проекта:

```text
Qwen3:8B
```

LLM используется для преобразования неструктурированных данных в структурированные признаки.

В частности:

```text
UserProfile   → UserFeatures
ResumeDocument → ResumeFeatures
Vacancy       → VacancyFeatures
```

Локальный запуск модели позволяет разрабатывать и тестировать систему без обязательной отправки пользовательских данных во внешний LLM API.

---

# RabbitMQ и Celery

RabbitMQ используется как брокер сообщений.

Celery используется для выполнения фоновых задач.

Тяжёлый LLM-анализ не выполняется непосредственно внутри HTTP-запроса.

Общий принцип:

```text
HTTP-запрос
    │
    ▼
сохранение данных
    │
    ▼
создание Celery Task
    │
    ▼
RabbitMQ
    │
    ▼
Celery Worker
    │
    ▼
LLM
    │
    ▼
сохранение результата
```

Это особенно важно для LLM-операций, которые могут занимать заметное время.

API отвечает за принятие и сохранение данных, а worker выполняет тяжёлую обработку независимо от HTTP-запроса.

---

## Celery Worker

Worker запускается отдельно от API.

Основная задача worker — выполнять фоновые LLM-операции.

Сейчас в Celery зарегистрированы задачи анализа пользовательского профиля и резюме.

Celery и RabbitMQ запускаются как отдельные сервисы Docker Compose.

Для текущей конфигурации RabbitMQ 4 используется настройка эксклюзивных очередей для control и events:

```python
celery_app.conf.update(
    control_queue_exclusive=True,
    event_queue_exclusive=True,
)
```

# UserFeatures

`UserFeatures` — это структурированное представление пользовательского профиля, подготовленное для последующего matching.

Текущая структура:

```text
UserFeatures
├── user_id
├── hard_constraints
├── preferences
├── tolerances
└── context
```

## Жёсткие ограничения

Условия, которые пользователь не готов принимать.

Например:

```text
- работа полностью в офисе;
- постоянные телефонные звонки;
- частые командировки.
```

Жёсткие ограничения должны формироваться только на основании действительно обязательных требований пользователя.

---

## Предпочтения

Условия, которые пользователь предпочитает, но потенциально готов рассматривать и другие варианты.

Например:

```text
- удалённая работа;
- небольшая команда;
- предсказуемая структура задач;
- гибкий график;
- интересные технические задачи.
```

Предпочтение не обязательно означает автоматическое исключение вакансии.

---

## Допустимые условия

Условия, которые пользователь способен принимать, даже если они не являются желательными.

Например:

```text
- редкие встречи;
- редкие переключения контекста;
- ограниченная многозадачность.
```

Допустимые условия должны отличаться от предпочтений и жёстких ограничений.

---

## Контекст

Дополнительная информация, необходимая для правильной интерпретации профиля.

Контекст не должен автоматически превращаться в обязательное условие.

# UserFeaturesExtractor

`UserFeaturesExtractor` преобразует `UserProfile` в структурированные признаки с помощью LLM.

Общий поток:

```text
UserProfile
    │
    ▼
USER_FEATURES_PROMPT
    │
    ▼
Ollama / Qwen3
    │
    ▼
JSON
    │
    ▼
UserFeatures
```

LLM должна:

* извлекать информацию только из профиля;
* разделять жёсткие ограничения, предпочтения и допустимые условия;
* использовать дополнительный контекст для интерпретации;
* не придумывать отсутствующие ограничения;
* не превращать каждое предпочтение в обязательное требование.

# Асинхронный анализ UserProfile

При создании или изменении профиля после успешного сохранения данных запускается:

```python
analyze_user_profile(user_id)
```

Поток:

```text
UserProfile
    │
    ▼
analyze_user_profile
    │
    ▼
RabbitMQ
    │
    ▼
Celery Worker
    │
    ▼
UserFeaturesExtractor
    │
    ▼
Ollama / Qwen3
    │
    ▼
UserFeatures
    │
    ▼
PostgreSQL
```

Задача:

1. получает `user_id`;
2. загружает актуальный `UserProfile`;
3. отправляет данные в LLM;
4. получает структурированные признаки;
5. создаёт `UserFeatures` либо обновляет существующую запись.

Таким образом, HTTP-запрос не ждёт завершения LLM-анализа.

# Работа с резюме

## ResumeDocument

`ResumeDocument` хранит текущее резюме пользователя и извлечённый из него текст.

Поддерживаются:

* PDF;
* DOCX.

Файлы используются только как источник текста.

Сам PDF или DOCX в PostgreSQL не хранится.

Общий поток:

```text
PDF / DOCX
    │
    ▼
извлечение текста
    │
    ▼
ResumeDocument
    │
    ▼
PostgreSQL
```

При повторной загрузке новое резюме заменяет предыдущее.

Endpoint:

```http
POST /profile/resume
```

---

# ResumeFeatures

`ResumeFeatures` содержит структурированные признаки, извлечённые из резюме с помощью LLM.

Текущая структура:

```text
ResumeFeatures
├── user_id
├── job_titles
├── hard_skills
├── soft_skills
├── experience
├── projects
├── weaknesses
├── strengths
└── experience_resume
```

### Формат полей

Большинство признаков представлены массивами строк:

```text
job_titles
hard_skills
soft_skills
projects
weaknesses
strengths
```

Опыт хранится отдельно как числовое значение:

```text
experience
```

Структурированный опыт работы хранится в `JSONB`:

```text
experience_resume
```

Это позволяет сохранять не только текстовое описание опыта, но и структуру отдельных мест работы:

```json
[
  {
    "position": "Младший разработчик",
    "company": "Компания",
    "period": "2024–2026",
    "description": "Описание работы"
  }
]
```

`JSONB` выбран вместо `TEXT[]`, поскольку результат LLM содержит структурированные объекты, а не просто список строк.

# Анализ вакансий

Вакансии проходят отдельный pipeline.

Исходные вакансии сначала сохраняются в MongoDB:

```text
Go Parser
    │
    ▼
MongoDB
    │
    ▼
Raw Vacancy
```

LLM-анализ вакансий не должен выполняться непосредственно при сборе каждой вакансии.

Планируемый поток:

```text
Все вакансии
     │
     ▼
Пакетная обработка
     │
     ▼
Предварительный отбор
     │
     ▼
Подходящие вакансии
     │
     ▼
Celery
     │
     ▼
RabbitMQ
     │
     ▼
Celery Worker
     │
     ▼
Ollama / Qwen3
     │
     ▼
VacancyFeatures
     │
     ▼
PostgreSQL
```

Основная задача следующего этапа — реализовать отложенную/периодическую обработку батчей уже собранных вакансий.

Такой подход позволяет:

* контролировать количество LLM-запросов;
* обрабатывать вакансии пакетами;
* повторно запускать анализ;
* не блокировать парсер;
* разделить сбор данных и дорогую обработку.

# VacancyFeatures

`VacancyFeatures` предназначен для хранения структурированного описания рабочей среды и профессиональных требований вакансии.

В дальнейшем эти данные станут основой для matching.

Предполагается разделять:

```text
профессиональные требования
        +
характеристики рабочей среды
        +
ограничения
        +
особенности нагрузки
```

# Matching

Matching — основной этап, ради которого строится вся предыдущая инфраструктура.

Итоговая система должна сопоставлять:

```text
                UserFeatures
                     │
                ResumeFeatures
                     │
                     ▼
               Matching Engine
                     ▲
                     │
              VacancyFeatures
                     │
                     ▼
                VacancyMatch
```

Matching должен учитывать несколько независимых аспектов.

## Профессиональное соответствие

Насколько пользователь соответствует профессиональным требованиям вакансии:

* профессия;
* должность;
* опыт;
* hard skills;
* технологии;
* проекты;
* другие профессиональные требования.

---

## Совместимость с рабочей средой

Насколько условия конкретной вакансии соответствуют профилю пользователя:

* график;
* формат работы;
* коммуникация;
* звонки;
* встречи;
* многозадачность;
* переключение контекста;
* информационная нагрузка;
* прерывания;
* дедлайны;
* автономность;
* размер команды;
* стиль управления;
* рабочая среда;
* командировки;
* другие параметры.

---

## Жёсткие ограничения

Если вакансия содержит условие, которое пользователь не готов принимать, оно должно отдельно учитываться в matching.

Жёсткие ограничения не должны смешиваться с обычными предпочтениями.

---

## Предпочтения

Предпочтительные характеристики должны влиять на итоговое соответствие, но не обязательно исключать вакансию.

---

## Допустимые условия

Условия, которые пользователь способен переносить, должны отличаться от предпочтений и жёстких ограничений.

## Объяснение результата

Итоговый `VacancyMatch` в дальнейшем должен не только содержать числовую оценку или результат сопоставления, но и объяснять:

* какие профессиональные требования совпали;
* какие условия рабочей среды подходят;
* какие ограничения соблюдены;
* какие предпочтения выполнены;
* какие потенциально проблемные условия были обнаружены.

# Авторизация

В проекте реализована JWT-аутентификация с подтверждением электронной почты.

Общий поток:

```text
Регистрация
    │
    ▼
Подтверждение email
    │
    ▼
Вход
    │
    ├───────────────┐
    ▼               ▼
Access token   Refresh token
    │               │
    ▼               │
API-запросы         │
    │               │
    └── истечение ──┘
                    │
                    ▼
             POST /auth/refresh
                    │
                    ▼
             новый Access token
```

Используются:

* Access token;
* Refresh token;
* Verification JWT;
* JWT-аутентификация;
* подтверждение email.

---

# Access Token

Access token представляет собой JWT.

Используется для авторизации запросов:

```http
Authorization: Bearer <access_token>
```

Текущий срок действия:

```text
1 час
```

---

# Refresh Token

Refresh token используется для получения нового Access token после его истечения.

Текущая реализация:

* refresh token является случайно сгенерированной строкой;
* refresh token не является JWT;
* срок действия — 30 дней;
* исходное значение не хранится в PostgreSQL;
* в базе хранится SHA-256 hash;
* на стадии MVP refresh token не ротируется.

Схема:

```text
Refresh token
      │
      ▼
    SHA-256
      │
      ▼
PostgreSQL
```

Endpoint:

```http
POST /auth/refresh
```

---

## 2. Предварительный отбор вакансий

До LLM-анализа необходимо сократить количество вакансий, которые проходят дорогую обработку.

Предварительный отбор должен использовать доступные структурированные данные вакансии и не требовать полного LLM-анализа.

# Ollama

NeuroHunter использует локально запущенную Ollama.

Проверка установленных моделей:

```bash
ollama list
```

Ожидаемая модель:

```text
qwen3:8b
```

Ollama запускается на host-машине.

Docker-контейнеры обращаются к ней через:

```text
http://host.docker.internal:11434
```

# Миграции

Создание миграции:

```bash
docker compose exec api \
  alembic revision --autogenerate -m "описание миграции"
```

Применение миграций:

```bash
docker compose exec api alembic upgrade head
```

Откат последней миграции:

```bash
docker compose exec api alembic downgrade -1
```

При изменении PostgreSQL-типа, для которого PostgreSQL не выполняет автоматическое преобразование, миграция должна быть проверена и при необходимости дополнена вручную.

# Текущий фокус

Базовая инфраструктура асинхронного LLM-анализа завершена.

Сейчас пользовательские данные проходят два независимых фоновых pipeline:

```text
UserProfile
    ↓
Celery
    ↓
RabbitMQ
    ↓
Celery Worker
    ↓
Ollama / Qwen3
    ↓
UserFeatures
    ↓
PostgreSQL
```

и

```text
ResumeDocument
    ↓
Celery
    ↓
RabbitMQ
    ↓
Celery Worker
    ↓
Ollama / Qwen3
    ↓
ResumeFeatures
    ↓
PostgreSQL
```

Следующий этап — обработка вакансий:

```text
MongoDB
    ↓
батч вакансий
    ↓
предварительный отбор
    ↓
Celery
    ↓
LLM
    ↓
VacancyFeatures
    ↓
PostgreSQL
```

После формирования всех трёх наборов признаков:

```text
UserFeatures
       +
ResumeFeatures
       +
VacancyFeatures
       ↓
Matching Engine
       ↓
VacancyMatch
```

На стадии MVP приоритет — получить полный работающий путь от исходных пользовательских данных и резюме до анализа вакансий и matching, не усложняя архитектуру раньше времени.
