# NeuroHunter

**NeuroHunter** — Open Source-сервис для анализа IT-вакансий и оценки их соответствия конкретному кандидату.

Проект собирает вакансии, анализирует их с помощью LLM, преобразует неструктурированные данные в структурированные характеристики и создаёт основу для персонализированного подбора вакансий.

Главная идея NeuroHunter — перейти от обычного поиска вакансий по ключевым словам к системе, которая учитывает одновременно **характеристики вакансии и характеристики конкретного пользователя**.

---

## Идея проекта

Обычный поиск вакансий в основном отвечает на вопрос:

> «Подхожу ли я этой вакансии по требованиям?»

NeuroHunter должен отвечать на другой вопрос:

> «Насколько эта вакансия подходит именно мне?»

Для этого система формирует две стороны будущего сопоставления:

```text
VacancyFeatures
       │
       │
       ▼
   Matching
       ▲
       │
       │
UserFeatures
```

`VacancyFeatures` описывает характеристики вакансии, а `UserFeatures` — характеристики пользователя, необходимые для персонализированного matching.

Дополнительным источником информации о пользователе является `PortfolioDocument`, который в дальнейшем может использоваться LLM для формирования и дополнения `UserFeatures`.

# Как работает система

## 1. Сбор вакансий

Go-парсер получает вакансии из Habr Career и извлекает исходные данные.

Полученная информация сохраняется в MongoDB.

MongoDB используется как хранилище исходных (`raw`) данных вакансий.

```text
Habr Career
     │
     ▼
Go Parser
     │
     ▼
MongoDB
```

Сохранение исходных данных отдельно от результата анализа позволяет повторно обрабатывать вакансии без необходимости повторного парсинга источника.

---

## 2. Анализ вакансий

Python-сервис получает исходные вакансии из MongoDB и передаёт их в LLM.

LLM анализирует текст вакансии и формирует структурированные характеристики.

Результат проходит валидацию через Pydantic и сохраняется в PostgreSQL.

```text
Raw Vacancy
     │
     ▼
Python Analyzer
     │
     ▼
LLM
     │
     ▼
VacancyFeatures
     │
     ▼
Pydantic Validation
     │
     ▼
PostgreSQL
```

LLM в данном случае выступает как слой преобразования неструктурированного текста в структурированные данные.

# `UserFeatures`

`UserFeatures` — отдельное структурированное представление пользователя, предназначенное непосредственно для дальнейшего анализа и vacancy matching.

В отличие от подробного `UserProfile`, `UserFeatures` содержит уже более компактный набор характеристик, который должен быть удобен для передачи и использования LLM.

Основные группы:

```text
UserFeatures
│
├── hard_constraints
├── preferences
├── tolerances
└── context
```

### `hard_constraints`

Жёсткие ограничения пользователя.

Это условия, нарушение которых должно существенно влиять на соответствие вакансии.

### `preferences`

Предпочтения пользователя.

Они описывают желательные, но не обязательно обязательные условия работы.

### `tolerances`

Допустимые для пользователя условия и нагрузки.

Этот набор характеристик позволяет отличать категорически неприемлемые условия от тех, которые пользователь способен принять.

### `context`

Дополнительный контекст, который помогает LLM лучше понимать пользователя.

Таким образом, `UserFeatures` является промежуточным представлением между подробной информацией о пользователе и будущим механизмом matching.

# `PortfolioDocument`

`PortfolioDocument` предназначен для хранения загруженного пользователем профессионального документа.

Модель содержит:

```text
PortfolioDocument
├── id
├── user_id
├── file_name
├── file_path
└── mime_type
```

Документ связан с пользователем отношением один-к-одному:

```text
User
 │
 └── PortfolioDocument
```

При этом в базе хранится не само содержимое файла, а информация, необходимая для работы с ним:

* имя файла;
* путь к файлу;
* MIME-тип.

Это позволяет хранить сам файл отдельно от PostgreSQL и не помещать бинарные данные непосредственно в таблицу.

# Анализ пользовательского портфолио

Следующий этап пользовательского LLM flow:

```text
PortfolioDocument
       │
       ▼
Извлечение содержимого
       │
       ▼
      LLM
       │
       ▼
UserFeatures
```

LLM должен использовать информацию из `PortfolioDocument` вместе с данными пользовательского профиля для формирования более точного `UserFeatures`.

На текущем этапе модели для этого сценария уже начали реализовываться.

Полноценный end-to-end сценарий:

```text
загрузка файла
      ↓
сохранение PortfolioDocument
      ↓
чтение содержимого
      ↓
передача в LLM
      ↓
формирование UserFeatures
      ↓
сохранение UserFeatures
```

ещё требует тестирования.

# Регистрация

```text
POST /auth/register
```

Пример запроса:

```json
{
  "email": "user@example.com",
  "password": "password123"
}
```

После регистрации создаётся пользователь.

Основные поля пользователя:

```text
users
├── id
├── email
├── hashed_password
├── is_active
├── is_superuser
└── is_verified
```

---

# Подтверждение email

После регистрации пользователь получает verification email.

Verification token представляет собой JWT и не хранится в PostgreSQL как отдельная запись.

Для токенов используются отдельные секреты:

```text
RESET_PASSWORD_TOKEN_SECRET
VERIFICATION_TOKEN_SECRET
```

Процесс подтверждения:

```text
Registration
      │
      ▼
Verification JWT
      │
      ▼
Email
      │
      ▼
Verification
      │
      ▼
is_verified = true
```

Frontend пока не реализован, поэтому endpoint `/auth/verify` тестируется напрямую через API.

После появления frontend verification URL сможет вести на frontend-страницу, которая передаст token в:

```text
POST /auth/verify
```

# Персонализированный matching

Главная цель NeuroHunter — сопоставлять пользователя с вакансией не только по совпадению ключевых навыков.

В будущем система должна сравнивать:

```text
UserProfile
     │
     ▼
UserFeatures
     │
     │
     ▼
Matching Engine
     ▲
     │
     │
VacancyFeatures
     │
     ▼
VacancyMatch
```

`UserFeatures` содержит:

* жёсткие ограничения;
* предпочтения;
* допустимые условия;
* дополнительный контекст.

`VacancyFeatures` содержит структурированные характеристики вакансии.

`Matching Engine` должен сравнивать эти данные и формировать результат соответствия.

На текущем этапе NeuroHunter уже содержит основной backend для сбора и анализа вакансий, а также реализованный фундамент пользовательского слоя.

Сейчас проект находится на переходе от **анализа отдельных вакансий** к **анализу пары «пользователь + вакансия»**.

Следующий крупный функциональный шаг — закончить обработку `PortfolioDocument`, протестировать получение `UserFeatures` через LLM и после этого перейти к реализации `VacancyMatch`.
