# NeuroHunter

NeuroHunter — сервис для персонализированного анализа вакансий.

Проект помогает ответить не только на вопрос:

> «Подхожу ли я этой вакансии?»

но и на вопрос:

> «Подходит ли эта работа мне?»

Основная идея проекта — разделять **профессиональное соответствие** и **совместимость с рабочей средой**.

Система должна учитывать не только профессию, навыки и опыт пользователя, но и особенности самой работы:

* график;
* формат работы;
* количество коммуникации;
* многозадачность;
* переключение контекста;
* дедлайны;
* уровень автономности;
* командировки;
* рабочую среду;
* другие параметры, влияющие на комфорт и нагрузку.

Цель — показывать не только результат подбора, но и объяснять, почему конкретная вакансия подходит или не подходит пользователю.

Проект находится в активной разработке.

# Основные компоненты

## Go Parser

Go-сервис отвечает за сбор вакансий:

* получение вакансий из источников;
* парсинг данных;
* формирование исходной структуры вакансии;
* сохранение вакансий в MongoDB;
* предотвращение появления дубликатов.

Исходные вакансии сохраняются отдельно от результатов анализа.

Это позволяет повторно запускать анализ уже собранных данных после изменения промпта, модели или логики обработки.

---

## MongoDB

MongoDB используется для хранения исходных вакансий.

В базе сохраняется исходное содержимое вакансии до дальнейшего анализа.

Разделение исходных данных и результатов анализа позволяет:

* повторно запускать анализ;
* менять промпты;
* менять LLM;
* изменять структуру признаков;
* не выполнять повторный парсинг уже собранных вакансий.

---

## Python Analyzer

Python-анализатор находится в:

```text
services/analyzer/
```

Он отвечает за:

* API на FastAPI;
* работу с PostgreSQL;
* пользовательские данные;
* авторизацию;
* интеграцию с LLM;
* извлечение структурированных признаков;
* фоновые задачи;
* подготовку данных для последующего сопоставления вакансий и пользователя.

---

## Ollama и Qwen3:8B

LLM работает локально через Ollama.

Основная модель проекта:

```text
Qwen3:8B
```

Модель используется для преобразования неструктурированных данных в структурированные признаки.

Использование локальной модели позволяет разрабатывать и тестировать систему без обязательной отправки пользовательских данных во внешний API.

# RabbitMQ и Celery

RabbitMQ используется как брокер сообщений, Celery — для выполнения фоновых задач.

Тяжёлый LLM-анализ не должен выполняться непосредственно внутри HTTP-запроса.

Общий принцип:

```text
HTTP-запрос
     │
     ▼
сохранение данных
     │
     ▼
создание Celery Task
     │
     ▼
RabbitMQ
     │
     ▼
Celery Worker
     │
     ▼
LLM
     │
     ▼
сохранение результата
```

## Текущий реализованный поток UserProfile

При создании или изменении профиля пользователя после успешного сохранения данных запускается задача:

```text
analyze_user_profile(user_id)
```

Далее:

```text
UserProfile
    │
    ▼
analyze_user_profile
    │
    ▼
RabbitMQ
    │
    ▼
Celery Worker
    │
    ▼
UserFeaturesExtractor
    │
    ▼
Ollama / Qwen3
    │
    ▼
UserFeatures
    │
    ▼
PostgreSQL
```

Задача получает `user_id`, самостоятельно загружает актуальный `UserProfile`, выполняет LLM-анализ и создаёт либо обновляет запись `UserFeatures`.

## Celery Worker

Worker запускается отдельно от API:

```text
Celery Worker
    │
    └── app.api.tasks.user_profile.analyze_user_profile
```

Celery и RabbitMQ работают как отдельная часть инфраструктуры Docker Compose.

Для совместимости с RabbitMQ 4.3 в конфигурации Celery используются эксклюзивные очереди для control и events:

```python
celery_app.conf.update(
    control_queue_exclusive=True,
    event_queue_exclusive=True,
)
```

## UserFeatures

`UserFeatures` — структурированное представление пользователя, предназначенное для последующего сопоставления с вакансиями.

Текущая структура:

```text
UserFeatures
├── hard_constraints
├── preferences
├── tolerances
└── context
```

### Жёсткие ограничения

Условия, нарушение которых делает вакансию неподходящей.

Например:

```text
- удалённая работа обязательна;
- ночная работа неприемлема;
- командировки неприемлемы.
```

При этом обычное предпочтение не должно автоматически становиться жёстким ограничением.

### Предпочтения

Условия, которые пользователь предпочитает, но потенциально может рассматривать не во всех случаях.

Например:

```text
- небольшой размер команды;
- предсказуемая структура задач;
- гибкий график;
- интересные задачи;
- профессиональный рост.
```

### Допустимые условия

Условия, которые пользователь способен переносить или принимать, даже если они не являются предпочтительными.

Например:

```text
- периодические встречи;
- ограниченная многозадачность;
- редкие командировки.
```

### Контекст

Дополнительная информация, которая помогает корректно интерпретировать профиль пользователя.

## UserFeaturesExtractor

`UserFeaturesExtractor` преобразует `UserProfile` в структурированные признаки с помощью LLM.

Общий поток:

```text
UserProfile
    │
    ▼
USER_FEATURES_PROMPT
    │
    ▼
Ollama / Qwen3
    │
    ▼
JSON
    │
    ▼
UserFeatures
```

LLM должна разделять информацию на:

* жёсткие ограничения;
* предпочтения;
* допустимые условия;
* дополнительный контекст.

LLM не должна придумывать отсутствующую информацию или автоматически превращать каждое предпочтение в обязательное требование.

# Работа с резюме

## ResumeDocument

`ResumeDocument` хранит текущее резюме пользователя и извлечённый из него текст.

Поддерживаются:

* PDF;
* DOCX.

Файлы используются для извлечения текста.

Общая схема:

```text
PDF / DOCX
    │
    ▼
Извлечение текста
    │
    ▼
ResumeDocument
    │
    ▼
ResumeFeatures
```

Сам PDF или DOCX в PostgreSQL не хранится.

При повторной загрузке новое резюме заменяет предыдущее.

Endpoint:

```text
POST /profile/resume
```

## ResumeFeatures

`ResumeFeatures` содержит признаки, извлечённые из резюме с помощью LLM.

Текущая структура:

```text
ResumeFeatures
├── job_titles
├── hard_skills
├── soft_skills
├── experience
├── projects
├── weaknesses
├── strengths
└── experience_resume
```

В дальнейшем эти данные будут использоваться совместно с `UserFeatures` при сопоставлении вакансий.

Асинхронная обработка резюме через Celery и сохранение `ResumeFeatures` в PostgreSQL находятся в работе.

```text

     │
     ▼
Пакетная обработка
     │
     ▼
  Celery
     │
     ▼

     │
     ▼
Celery Worker
     │
     ▼
Ollama / Qwen3
     │
     ▼
VacancyFeatures
     │
     ▼

```

Не предполагается отправлять каждую найденную вакансию на полный LLM-анализ.

Перед дорогим анализом планируется выполнять предварительный отбор, чтобы уменьшить количество вакансий, проходящих через LLM и последующий matching.

Целевая схема:

```text
Все вакансии
      │
      ▼
Предварительный отбор
      │
      ▼
Подходящие кандидаты
      │
      ▼
LLM-анализ
      │
      ▼
VacancyFeatures
      │
      ▼
Matching
```

# Авторизация

В проекте реализована JWT-аутентификация с подтверждением электронной почты.

Текущий поток:

```text
Регистрация
    │
    ▼
Подтверждение email
    │
    ▼
Вход
    │
    ├───────────────┐
    ▼               ▼
Access token   Refresh token
    │               │
    ▼               │
API-запросы         │
    │               │
    └── истечение ──┘
                    │
                    ▼
             POST /auth/refresh
                    │
                    ▼
             Новый Access token
```

Поддерживается:

* регистрация;
* JWT-аутентификация;
* получение текущего пользователя;
* подтверждение электронной почты;
* отправка письма подтверждения;
* Access token;
* Refresh token;
* обновление Access token.

## Access token

Access token представляет собой JWT.

Используется для авторизации обычных запросов к API:

```text
Authorization: Bearer <access_token>
```

Текущий срок действия:

```text
1 час
```

## Refresh token

Refresh token используется для получения нового Access token после его истечения.

Он:

* представляет собой случайно сгенерированную строку;
* не является JWT;
* имеет срок действия 30 дней;
* хранится у клиента;
* не хранится в исходном виде в PostgreSQL.

В базе данных хранится только SHA-256 хеш Refresh token.

Схема:

```text
случайный Refresh token
        │
        ▼
      SHA-256
        │
        ▼
    PostgreSQL
```

При обновлении:

```text
Refresh token клиента
        │
        ▼
      SHA-256
        │
        ▼
поиск хеша в PostgreSQL
        │
        ▼
проверка существования
        │
        ▼
проверка срока действия
        │
        ▼
создание нового JWT
```

Endpoint:

```text
POST /auth/refresh
```

Пример:

```text
POST /auth/refresh?refresh_token=<refresh_token>
```

Ответ:

```json
{
  "access_token": "<новый_access_token>",
  "refresh_token": "<текущий_refresh_token>",
  "token_type": "bearer"
}
```

На стадии MVP Refresh token не ротируется.

То есть после обновления Access token используется тот же Refresh token до окончания его срока действия.

> Механизм Access / Refresh token реализован как временное решение для стадии MVP.

Более сложные механизмы управления сессиями, ротации Refresh token, отзыва токенов и другие аспекты безопасности могут быть пересмотрены перед переходом проекта в production.

# Запуск

## Требования

Для локального запуска необходимы:

* Docker
* Docker Compose
* Go
* Python
* Poetry
* Ollama
* Qwen3:8B

---

## Установка Python-зависимостей

```bash
cd services/analyzer
poetry install
```

---

## Запуск проекта

Из корня проекта:

```bash
docker compose up -d --build
```

Проверка контейнеров:

```bash
docker compose ps
```

Логи API:

```bash
docker compose logs -f api
```

Логи Celery:

```bash
docker compose logs -f celery
```

---

# Ollama

NeuroHunter использует локально запущенную Ollama.

Проверка установленных моделей:

```bash
ollama list
```

Ожидаемая модель:

```text
qwen3:8b
```

Ollama запускается на хост-машине.

Docker-контейнеры обращаются к ней через:

```text
http://host.docker.internal:11434
```

---

# Миграции

Создание миграции:

```bash
docker compose exec api \
  alembic revision --autogenerate -m "описание миграции"
```

Применение миграций:

```bash
docker compose exec api alembic upgrade head
```

Откат последней миграции:

```bash
docker compose exec api alembic downgrade -1
```

---

# Тестирование

Запуск всех тестов:

```bash
docker compose exec api pytest
```

Запуск отдельного теста анализатора резюме:

```bash
docker compose exec api pytest -s \
  app/tests/llm/test_extractor.py::test_resume_extract_features
```

LLM-тесты используют локальную Ollama.

# Текущий фокус

Проект находится в активной разработке.

Текущий фокус — завершение асинхронного LLM-пайплайна на базе Celery + RabbitMQ.

На данный момент реализован асинхронный анализ `UserProfile`:

```text
UserProfile
    ↓
Celery
    ↓
RabbitMQ
    ↓
Celery Worker
    ↓
Ollama / Qwen3
    ↓
UserFeatures
    ↓
PostgreSQL
```

Следующий этап — перенести тот же подход на обработку `ResumeDocument`, после чего основной фокус будет смещён на обработку вакансий и персонализированное сопоставление пользователя с рабочими условиями.

На стадии MVP приоритет — получить полный работающий путь от пользовательских данных и резюме до анализа вакансий и matching, не усложняя инфраструктуру до перехода проекта в production.
