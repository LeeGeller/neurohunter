# NeuroHunter

NeuroHunter — сервис для персонализированного анализа вакансий.

Проект помогает ответить не только на вопрос:

> **«Подхожу ли я этой вакансии?»**

но и на вопрос:

> **«Подходит ли эта работа мне?»**

Основная идея проекта — разделять **профессиональное соответствие** и **совместимость с рабочей средой**.

Система должна учитывать не только профессию, навыки и опыт пользователя, но и особенности самой работы: график, количество коммуникации, многозадачность, переключение контекста, уровень автономности, формат работы, командировки, рабочую среду и другие параметры.

Цель — показывать не только результат подбора, но и объяснять, **почему конкретная вакансия подходит или не подходит пользователю**.

Проект находится в активной разработке.

---

# Архитектура

Основной поток обработки вакансий:

```text
                         Источник вакансий
                                │
                                ▼
                           Go Parser
                                │
                                ▼
                             MongoDB
                         исходные вакансии
                                │
                         пакетная обработка
                                │
                                ▼
                             Celery
                                │
                                ▼
                           RabbitMQ
                                │
                                ▼
                           LLM Worker
                                │
                                ▼
                           Ollama / Qwen
                                │
                                ▼
                       VacancyFeatures
                                │
                                ▼
                           PostgreSQL
                                │
                                ▼
                        Matching Engine
                                ▲
                   ┌────────────┴────────────┐
                   │                         │
             UserFeatures             ResumeFeatures
                   ▲                         ▲
                   │                         │
              UserProfile             ResumeDocument
```

Пользовательские данные проходят отдельный асинхронный поток:

```text
UserProfile / ResumeDocument
             │
             ▼
           Celery
             │
             ▼
          RabbitMQ
             │
             ▼
         LLM Worker
             │
             ▼
 UserFeatures / ResumeFeatures
```

Изменение исходных данных пользователя в дальнейшем должно приводить к повторному анализу соответствующих признаков.

# Основные компоненты

## Go Parser

Go-сервис отвечает за сбор вакансий:

* получение вакансий из источников;
* парсинг данных;
* формирование исходной структуры вакансии;
* сохранение вакансий в MongoDB;
* предотвращение появления дубликатов.

Исходные вакансии сохраняются отдельно от результатов анализа.

Это позволяет повторно анализировать уже собранные данные после изменения промпта, модели или логики обработки.

---

## MongoDB

MongoDB используется для хранения исходных вакансий.

В базе сохраняется исходное содержимое вакансии до её дальнейшего анализа.

Разделение исходных данных и результатов анализа позволяет:

* повторно запускать анализ;
* менять промпты;
* менять LLM;
* изменять структуру признаков;
* не выполнять повторный парсинг уже собранных вакансий.

---

## Python Analyzer

Python-анализатор находится в:

```text
services/analyzer/
```

Он отвечает за:

* API на FastAPI;
* работу с PostgreSQL;
* пользовательские данные;
* авторизацию;
* интеграцию с LLM;
* извлечение структурированных признаков;
* подготовку данных для последующего сопоставления вакансий и пользователя.

---

## Ollama и Qwen3:8B

LLM работает локально через Ollama.

Модель используется для преобразования неструктурированного текста в структурированные признаки.

Основная модель проекта:

```text
Qwen3:8B
```

Использование локальной модели позволяет разрабатывать и тестировать систему без обязательной отправки пользовательских данных во внешний API.

---

## RabbitMQ и Celery

RabbitMQ используется как брокер сообщений, Celery — для выполнения фоновых задач.

Тяжёлый LLM-анализ не должен выполняться непосредственно внутри HTTP-запроса.

Основные типы фоновых задач:

```text
UserFeatures
ResumeFeatures
VacancyFeatures
VacancyMatch
```

Общая схема:

```text
HTTP-запрос
    │
    ▼
сохранение данных
    │
    ▼
создание задачи
    │
    ▼
RabbitMQ
    │
    ▼
Celery Worker
    │
    ▼
LLM
```

## UserFeatures

`UserFeatures` — структурированное представление пользователя, предназначенное для последующего сопоставления с вакансиями.

Текущая структура:

```text
UserFeatures
├── hard_constraints
├── preferences
├── tolerances
└── context
```

### Жёсткие ограничения

Условия, нарушение которых делает вакансию неподходящей независимо от остальных характеристик.

### Предпочтения

Условия, которые пользователь предпочитает, но может быть готов рассматривать не во всех случаях.

### Допустимые условия

Условия, которые пользователь способен переносить или принимать.

### Контекст

Дополнительная информация, которая помогает LLM корректнее интерпретировать профиль пользователя.

# Работа с резюме

## ResumeDocument

`ResumeDocument` хранит текущее резюме пользователя и извлечённый из него текст.

Поддерживаются:

* PDF;
* DOCX.

Файлы используются для извлечения текста.

Общая схема:

```text
PDF / DOCX
    │
    ▼
Извлечение текста
    │
    ▼
ResumeDocument
    │
    ▼
ResumeFeatures
```

Сам PDF или DOCX в PostgreSQL не хранится.

При повторной загрузке новое резюме заменяет предыдущее.

Endpoint:

```text
POST /profile/resume
```

---

## ResumeFeatures

`ResumeFeatures` содержит признаки, извлечённые из резюме с помощью LLM.

Текущая структура:

```text
ResumeFeatures
├── job_titles
├── hard_skills
├── soft_skills
├── experience
├── projects
├── weaknesses
├── strengths
└── experience_resume
```

В дальнейшем эти данные будут использоваться совместно с `UserFeatures` при сопоставлении вакансий.

# Анализ вакансий

Основной поток обработки вакансии:

```text
Raw Vacancy
     │
     ▼
  MongoDB
     │
     ▼
Пакетная обработка
     │
     ▼
  Celery
     │
     ▼
 RabbitMQ
     │
     ▼
 LLM Worker
     │
     ▼
VacancyFeatures
```

Не предполагается отправлять каждую найденную вакансию на полный LLM-анализ.

Перед дорогим анализом планируется выполнять предварительный отбор, чтобы уменьшить количество вакансий, проходящих через LLM и последующий matching.

Целевая схема:

```text
Все вакансии
     │
     ▼
Предварительный отбор
     │
     ▼
Подходящие кандидаты
     │
     ▼
LLM-анализ
     │
     ▼
VacancyFeatures
     │
     ▼
Matching
```

# Matching

Целевая система сопоставления:

```text
                 UserFeatures
                      │
                      │
                 ResumeFeatures
                      │
                      ▼
                Matching Engine
                      ▲
                      │
                VacancyFeatures
                      │
                      ▼
                 VacancyMatch
```

Matching должен учитывать несколько независимых аспектов.

### Профессиональное соответствие

Насколько пользователь соответствует требованиям вакансии:

* профессия;
* опыт;
* навыки;
* технологии;
* проекты;
* другие профессиональные требования.

### Совместимость с рабочей средой

Насколько условия работы соответствуют профилю пользователя:

* график;
* формат работы;
* коммуникация;
* многозадачность;
* переключение контекста;
* дедлайны;
* автономность;
* рабочая среда;
* командировки;
* другие параметры.

### Жёсткие ограничения

Отдельно должны учитываться условия, которые пользователь не готов принимать.

### Предпочтения

Предпочтительные характеристики работы должны влиять на итоговое сопоставление, но не обязательно исключать вакансию.

### Допустимые условия

Допустимые пользователем нагрузки должны отличаться от его предпочтений и жёстких ограничений.

# Авторизация

В проекте реализована JWT-аутентификация с подтверждением электронной почты.

Текущий поток:

```text
Регистрация
    │
    ▼
Подтверждение email
    │
    ▼
Вход
    │
    ├───────────────┐
    ▼               ▼
Access token   Refresh token
    │               │
    ▼               │
API-запросы         │
    │               │
    │               │
    └── истечение ──┘
                    │
                    ▼
             POST /auth/refresh
                    │
                    ▼
             Новый Access token
```

Поддерживается:

* регистрация;
* JWT-аутентификация;
* получение текущего пользователя;
* подтверждение электронной почты;
* отправка письма подтверждения;
* Access token;
* Refresh token;
* обновление Access token.

---

## Access token

Access token представляет собой JWT.

Он используется для авторизации обычных запросов к API:

```http
Authorization: Bearer <access_token>
```

Текущий срок действия Access token:

```text
1 час
```

---

## Refresh token

Refresh token используется для получения нового Access token после его истечения.

Он:

* представляет собой случайно сгенерированную строку;
* не является JWT;
* имеет срок действия 30 дней;
* хранится у клиента;
* не хранится в исходном виде в PostgreSQL.

В базе данных хранится только SHA-256 хеш Refresh token.

Схема:

```text
случайный Refresh token
        │
        ▼
      SHA-256
        │
        ▼
PostgreSQL
```

При обновлении токена:

```text
Refresh token клиента
        │
        ▼
      SHA-256
        │
        ▼
поиск хеша в PostgreSQL
        │
        ▼
проверка существования
        │
        ▼
проверка срока действия
        │
        ▼
создание нового JWT
```

---

## Обновление Access token

Endpoint:

```text
POST /auth/refresh
```

Пример:

```text
POST /auth/refresh?refresh_token=<refresh_token>
```

Ответ:

```json
{
  "access_token": "<новый_access_token>",
  "refresh_token": "<текущий_refresh_token>",
  "token_type": "bearer"
}
```

На стадии MVP Refresh token **не ротируется**.

То есть после обновления Access token используется тот же Refresh token до окончания его срока действия.

### Важно

Текущий механизм авторизации является **временным решением для стадии MVP**.

На данном этапе задача — реализовать простой рабочий цикл:

```text
login
  ↓
access token
  ↓
истечение access token
  ↓
refresh token
  ↓
новый access token
```

Более сложные механизмы управления сессиями, ротации Refresh token, отзыва токенов и других аспектов безопасности могут быть пересмотрены перед переходом проекта в production.

Запуск отдельного теста анализатора резюме:

  app/tests/llm/test_extractor.py::test_resume_extract_features

# Текущий фокус

Проект находится в активной разработке.

Текущий фокус — завершение асинхронного LLM-пайплайна на базе **Celery + RabbitMQ**, после чего основной фокус будет смещён на обработку вакансий и персонализированное сопоставление пользователя с рабочими условиями.

На стадии MVP приоритет — получить **полный работающий путь от регистрации пользователя и его данных до анализа и сопоставления вакансий**, не усложняя инфраструктуру до перехода проекта в production.
