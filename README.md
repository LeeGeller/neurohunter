# NeuroHunter

**NeuroHunter** — open-source сервис для персонализированного поиска и анализа вакансий.

Цель проекта — не просто найти вакансии, соответствующие профессии, навыкам и опыту кандидата, но и оценить, насколько условия и организация работы подходят конкретному человеку.

Обычный поиск работы преимущественно отвечает на вопрос:

> Подходит ли кандидат работодателю?

NeuroHunter стремится ответить на два других вопроса:

- Насколько вакансия соответствует профессиональному профилю кандидата?
- Насколько рабочая среда, нагрузка и организация работы соответствуют индивидуальным потребностям человека?

Для этого проект объединяет сбор вакансий, структурированную обработку пользовательских данных, первичную фильтрацию, LLM-анализ и персонализированное сопоставление.

Проект находится в активной разработке. Текущая задача — завершить поисковый pipeline и первичную фильтрацию, после чего перейти к анализу вакансий и matching.

---

# Основная идея

NeuroHunter должен автоматически находить вакансии, отбирать подходящие по объективным условиям, анализировать особенности работы и оценивать совместимость каждой вакансии с конкретным пользователем.

При этом поиск, анализ и сопоставление разделены на отдельные этапы.

**1. Поиск вакансий**

Система использует профессиональные направления пользователей для формирования поисковых запросов. Одинаковые запросы объединяются, чтобы не выполнять один и тот же поиск повторно для разных пользователей.

**2. Первичная фильтрация**

Полученные вакансии проверяются по структурированным критериям: зарплате, формату работы, месту работы, опыту, типу занятости и графику.

На этом этапе отсекаются вакансии, которые не подходят ни одному пользователю.

**3. LLM-анализ**

Для вакансий, прошедших первичный отбор, извлекаются структурированные характеристики: требования, условия труда, коммуникация, рабочая среда, нагрузка и другие особенности.

**4. Matching**

Система сопоставляет характеристики вакансии с профессиональными данными пользователя, его резюме, жёсткими ограничениями, предпочтениями и допустимыми условиями.

Результат — персонализированная оценка вакансии с объяснением причин соответствия и возможных несовпадений.


Это целевой процесс системы. Отдельные его этапы уже реализованы, остальные находятся в разработке.

## Основные архитектурные принципы

- Поиск вакансий отделён от их семантического анализа.
- Первичная фильтрация выполняется до дорогостоящей LLM-обработки.
- Пользовательские данные отделены от исходных данных вакансий.
- Исходная вакансия отделена от результатов её анализа.
- Одна вакансия может подходить нескольким пользователям.
- Одинаковые поисковые запросы выполняются один раз для всех заинтересованных пользователей.
- Результаты поиска должны проходить дедупликацию.
- LLM-анализ выполняется для релевантных вакансий, а не для всего объёма найденных данных.
- Итоговый matching выполняется отдельно для каждой пары «вакансия — пользователь».
- Фоновые задачи позволяют организовать периодический поиск и асинхронную обработку.

# Основные компоненты

## Python Analyzer

Расположение:

```text
services/analyzer/
```

Python Analyzer отвечает за пользовательский домен, API и оркестрацию обработки данных.

Основные задачи:

- FastAPI;
- регистрация и авторизация пользователей;
- работа с PostgreSQL;
- работа с пользовательскими профилями;
- формирование `UserFeatures`;
- обработка резюме;
- формирование `ResumeFeatures`;
- предоставление пользовательских данных другим компонентам через API;
- управление фоновыми задачами через Celery;
- LLM-анализ;
- подготовка результатов для matching.

Python Analyzer выступает владельцем пользовательских данных. Go Parser получает только те данные, которые необходимы ему для поиска и первичной фильтрации, через отдельный интерфейс взаимодействия.

## Go Parser

Go Parser отвечает за сбор вакансий и их первичную обработку.

Текущий источник вакансий — Habr Career.

Основные задачи:

- получение поисковых групп;
- выполнение поисковых запросов;
- парсинг вакансий;
- нормализация данных;
- формирование модели `Vacancy`;
- дедупликация;
- первичная фильтрация;
- определение пользователей, для которых вакансия прошла фильтрацию;
- сохранение подходящих вакансий;
- передача результатов на дальнейший анализ.

Go Parser не должен зависеть от внутренней ORM-модели Python Analyzer или напрямую обращаться к PostgreSQL за пользовательскими данными.

## PostgreSQL

PostgreSQL используется для хранения структурированных и реляционных данных:

- пользователи;
- `UserProfile`;
- `UserFeatures`;
- `ResumeDocument`;
- `ResumeFeatures`;
- результаты анализа вакансий;
- результаты matching.

Доступ к данным реализуется через соответствующие компоненты приложения.

## MongoDB

MongoDB используется для хранения исходных вакансий.

Это позволяет повторно анализировать собранные данные без повторного обращения к внешним источникам.

В целевом pipeline вакансии, не прошедшие первичную фильтрацию ни для одного пользователя, не должны передаваться на дальнейший анализ.

## RabbitMQ и Celery

RabbitMQ используется в качестве брокера сообщений, а Celery — для выполнения фоновых задач.

Основные сценарии:

- анализ пользовательского профиля;
- анализ резюме;
- запуск поиска вакансий;
- асинхронная обработка отобранных вакансий;
- пакетный LLM-анализ;
- периодический запуск поиска через Celery Beat.

Периодическая автоматизация поиска относится к следующим этапам разработки.

## Ollama и Qwen3

Для локального LLM-анализа используется Ollama с моделью Qwen3:8B.

Модель применяется для преобразования неструктурированных данных в структурированные характеристики:

```text
UserProfile    → UserFeatures
ResumeDocument → ResumeFeatures
Vacancy        → VacancyFeatures
```

Полученные результаты используются последующими этапами обработки и сопоставления.

# Пользовательские данные

## UserProfile

`UserProfile` содержит исходные сведения о пользователе и его предпочтениях относительно работы.

Профиль может включать:

- профессию;
- опыт;
- образование;
- желаемый рабочий график;
- формат работы;
- отношение к переработкам;
- работу по выходным и ночью;
- командировки;
- физическую нагрузку;
- коммуникацию;
- встречи и звонки;
- многозадачность;
- переключение контекста;
- дедлайны;
- информационную нагрузку;
- предпочтительный размер команды;
- стиль управления;
- автономность;
- особенности рабочей среды;
- мотивационные факторы;
- дополнительное описание пользователя.

Исходный профиль служит основой для формирования структурированных характеристик.

## UserFeatures

`UserFeatures` — структурированное представление пользовательского профиля, подготовленное для дальнейшей обработки.

```text
UserFeatures
├── job_titles
├── hard_constraints
├── preferences
├── tolerances
└── context
```

### job_titles

`job_titles` содержит названия профессиональных направлений и должностей, используемые для поиска вакансий.

Они формируются на основе профессии, опыта, специализации, технологий и профессионального направления пользователя.

Пример:

```text
Python Backend Developer
Backend Developer
Python Developer
Django Developer
```

Названия нормализуются, а совпадающие варианты группируются.

Если несколько пользователей заинтересованы в одном поисковом запросе, система должна выполнить этот поиск один раз и сохранить информацию о всех пользователях, для которых предназначены его результаты.

Нормализация написания не заменяет семантическое сопоставление профессий. Разные названия должностей могут оставаться отдельными запросами, если их автоматическое объединение способно изменить результаты поиска.

### hard_constraints

`hard_constraints` содержит жёсткие ограничения пользователя.

Это условия, нарушение которых может сделать вакансию неприемлемой.

Примеры:

- минимальный уровень оплаты;
- допустимый формат работы;
- отсутствие ночной работы;
- отсутствие командировок;
- отсутствие физической нагрузки;
- другие обязательные условия.

Для первичной фильтрации ограничения должны быть представлены в структурированном виде, пригодном для проверки по данным вакансии.

Человекочитаемые описания ограничений сами по себе не заменяют структурированные критерии фильтрации.

### preferences

`preferences` содержит характеристики работы, которые пользователь предпочитает.

Например:

- небольшая команда;
- спокойная рабочая среда;
- автономность;
- понятные задачи;
- минимальное количество встреч;
- профессиональное развитие.

Предпочтения учитываются преимущественно на этапе matching и не всегда должны приводить к исключению вакансии.

### tolerances

`tolerances` описывает условия, которые пользователь способен принимать, даже если они не являются предпочтительными.

Например, пользователь может предпочитать редкие встречи, но быть готовым к периодическому общению с коллегами.

Эти данные позволяют оценивать совместимость более гибко, чем простое совпадение или несовпадение предпочтений.

### context

`context` содержит дополнительную информацию, необходимую для интерпретации пользовательского профиля.

Она может включать профессиональные сведения, технологии, описание предпочтений и другие обстоятельства, полезные для LLM-анализа и matching.

# Подготовка поисковых запросов

Для поиска используется информация из `UserFeatures.job_titles`.

`SearchUserFeaturesService` получает пользовательские данные и формирует группы по нормализованным названиям должностей.

Результат группировки представляет собой структуру:

```python
{
    "python developer": [
        user_id_1,
        user_id_2,
    ],
    "backend developer": [
        user_id_1,
        user_id_3,
    ],
}
```

Каждому уникальному названию соответствует список пользователей, для которых нужно выполнить поиск.

Подготовка поисковых групп выполняется в Python. Go Parser получает эти группы через внутренний API, после чего самостоятельно выполняет поиск и первичную фильтрацию.

Целевой процесс:

```text
UserFeatures всех пользователей
              │
              ▼
           job_titles
              │
              ▼
        Нормализация
              │
              ▼
       Группировка пользователей
              │
              ▼
     job_title → user_ids
              │
              ▼
        Внутренний API
              │
              ▼
           Go Parser
```

Такое разделение позволяет не дублировать пользовательскую логику в Go и не связывать поисковый компонент с внутренней структурой PostgreSQL.

# Поиск вакансий

Поиск выполняется по уникальным поисковым группам, сформированным на основании пользовательских `job_titles`.

Текущий источник — Habr Career. В дальнейшем архитектура должна допускать подключение дополнительных источников вакансий.

Целевой процесс:

```text
Поисковые группы
       │
       ▼
   Go Parser
       │
       ▼
  Поиск по каждому
  уникальному запросу
       │
       ▼
  Полученные вакансии
       │
       ▼
 Нормализация данных
       │
       ▼
  Первичная фильтрация
       │
       ▼
  Дедупликация
       │
       ▼
Сохранение релевантных вакансий
```

Поиск не должен выполняться отдельно для каждого пользователя, если запросы совпадают.

# Vacancy

`Vacancy` представляет исходную вакансию, полученную из внешнего источника.

Основные поля:

```text
ID
Title
Company
WorkLocation
WorkFormat
URL
Description
SalaryFrom
SalaryTo
Currency
VacancyDate
```

`Vacancy` не зависит от конкретного пользователя. Она описывает саму вакансию, а не результат её соответствия определённому кандидату.

Такое разделение позволяет повторно использовать одну и ту же вакансию для разных пользователей, проводить дедупликацию и анализировать исходные данные независимо от результатов LLM.

# Первичная фильтрация

Первичная фильтрация — обязательный этап между сбором вакансий и их семантическим анализом.

Её задача — исключить вакансии, которые не проходят обязательные условия пользователя, до передачи на дорогостоящую LLM-обработку.

Фильтрация выполняется на основании структурированных критериев пользователя и данных вакансии.

Основные параметры:

- зарплата;
- формат работы;
- место работы;
- требуемый опыт;
- тип занятости;
- рабочий график.

## Принцип работы

Поисковая группа содержит название должности и список пользователей, заинтересованных в результатах поиска.

Полученные вакансии проверяются отдельно для каждого пользователя:

```text
Поисковая группа
       │
       ▼
Полученные вакансии
       │
       ▼
   Vacancy
       │
       ▼
Проверка обязательных условий
       │
       ├── User 1
       ├── User 2
       └── User 3
               │
               ▼
    Пользователи, прошедшие
       первичный фильтр
```

Одна вакансия может пройти фильтрацию для нескольких пользователей, одного пользователя или не пройти ни для кого.

Вакансия сохраняется для дальнейшей обработки только в том случае, если она подходит хотя бы одному пользователю.

Если обязательные условия не выполняются, вакансия не должна передаваться на LLM-анализ.

Первичная фильтрация выполняется обычной программной логикой Go. LLM не используется вместо структурных проверок.

# Связь Vacancy и User

После первичной фильтрации система должна сохранить информацию о том, каким пользователям подходит каждая вакансия.

Для этого предусмотрена связь многие-ко-многим:

```text
Vacancy A
├── User 1
└── User 3

Vacancy B
└── User 2
```

Одна вакансия может подойти нескольким пользователям, а одному пользователю может соответствовать множество вакансий.

Эта связь отражает прохождение первичного отбора и **не является итоговым matching**.

На данном этапе система определяет, какие пары «вакансия — пользователь» имеет смысл передавать на дальнейший анализ.

Хранение этой связи позволит:

- не выполнять повторный поиск для каждого пользователя;
- учитывать результаты фильтрации отдельно для каждого пользователя;
- исключать вакансии, которые не подходят никому;
- передавать на дальнейшую обработку только релевантные пары;
- отделять первичный отбор от итоговой оценки совместимости.

Модель связи `Vacancy ↔ User` и её сохранение относятся к этапам дальнейшей разработки поискового pipeline.

# Анализ вакансий

## VacancyFeatures

`VacancyFeatures` — структурированное представление характеристик вакансии, полученное после её анализа.

В отличие от `Vacancy`, содержащей исходные данные, `VacancyFeatures` описывает извлечённые из вакансии требования, условия и особенности рабочего процесса.

Основные группы признаков:

### Профессиональные требования

- должность;
- навыки;
- технологии;
- опыт;
- образование;
- требования к кандидату.

### Условия работы

- зарплата;
- график;
- формат работы;
- место работы;
- тип занятости;
- командировки;
- физическая нагрузка.

### Коммуникация

- взаимодействие с клиентами;
- взаимодействие с коллегами;
- встречи;
- звонки;
- публичные выступления;
- конфликтные ситуации.

### Организация работы

- многозадачность;
- частота переключения контекста;
- прерывания;
- дедлайны;
- информационная нагрузка;
- автономность;
- определённость требований.

### Рабочая среда

- размер команды;
- стиль управления;
- уровень шума;
- организация рабочего пространства;
- интенсивность коммуникации;
- другие особенности рабочей среды.

Фактический состав `VacancyFeatures` определяется моделью данных проекта и результатами анализа доступной информации.

Не все характеристики могут быть явно указаны в описании вакансии. Поэтому при формировании признаков необходимо учитывать полноту и достоверность исходных данных, а отсутствие информации не следует автоматически трактовать как подтверждение конкретного условия.

# Фоновая обработка и периодический поиск

Для выполнения ресурсоёмких задач используется Celery, а RabbitMQ выступает брокером сообщений.

После первичной фильтрации отобранные вакансии должны передаваться на асинхронный LLM-анализ.

Целевой процесс:

```text
Первичная фильтрация
         │
         ▼
Отобранные вакансии
         │
         ▼
      Celery
         │
         ▼
   RabbitMQ
         │
         ▼
  Celery Worker
         │
         ▼
  Ollama / Qwen3
         │
         ▼
  VacancyFeatures
         │
         ▼
      Хранилище
```

Это позволит выполнять анализ отдельно от сбора вакансий и контролировать нагрузку на локальную LLM.

В дальнейшем Celery Beat будет запускать поиск по расписанию. Автоматический процесс должен обеспечивать повторяемость запуска, предотвращение ненужной повторной обработки и возможность продолжить работу после временных сбоев.

# Matching

Matching — этап персонализированной оценки вакансий для пользователей, прошедших первичную фильтрацию.

Он использует три источника структурированных данных:

```text
UserFeatures
     +
ResumeFeatures
     +
VacancyFeatures
     │
     ▼
 Matching Engine
     │
     ▼
 VacancyMatch
```

## Профессиональное соответствие

Система оценивает соответствие профиля пользователя и резюме требованиям вакансии:

- должность;
- опыт;
- навыки;
- технологии;
- проекты;
- образование;
- профессиональные требования.

## Совместимость с рабочей средой

Система сопоставляет условия и организацию работы с характеристиками пользователя:

- график;
- формат работы;
- коммуникация;
- встречи;
- звонки;
- многозадачность;
- переключение контекста;
- информационная нагрузка;
- дедлайны;
- автономность;
- размер команды;
- стиль управления;
- рабочая среда;
- командировки;
- другие особенности рабочего процесса.

## Индивидуальные ограничения и предпочтения

При оценке учитываются:

- жёсткие ограничения;
- предпочтения;
- допустимые условия;
- контекст пользователя.

Предпочтения и допустимые условия не должны автоматически интерпретироваться как запреты. Matching должен различать обязательные требования и факторы, влияющие на итоговую оценку.

## VacancyMatch

`VacancyMatch` представляет результат сопоставления конкретной вакансии с конкретным пользователем.

В целевой реализации результат должен позволять понять:

- насколько вакансия подходит профессионально;
- насколько условия работы совместимы с потребностями пользователя;
- какие условия соответствуют ограничениям и предпочтениям;
- какие несовпадения обнаружены;
- на каких данных основана оценка.

Итоговый результат предназначен не только для ранжирования вакансий, но и для объяснения причин соответствия и несоответствия.

# Обработка резюме

Проект поддерживает загрузку и обработку резюме в форматах PDF и DOCX.

Целевой поток:

```text
PDF / DOCX
     │
     ▼
Извлечение текста
     │
     ▼
ResumeDocument
     │
     ▼
Celery
     │
     ▼
Ollama / Qwen3
     │
     ▼
ResumeFeatures
     │
     ▼
PostgreSQL
```

`ResumeDocument` представляет исходный документ и извлечённые из него данные.

`ResumeFeatures` содержит структурированные профессиональные характеристики, необходимые для сопоставления резюме с требованиями вакансий.

# Авторизация

В проекте реализуется JWT-аутентификация с подтверждением электронной почты.

Основные функции:

- регистрация пользователя;
- подтверждение email;
- Access Token;
- Refresh Token;
- проверка авторизации;
- восстановление доступа к аккаунту.

Access Token используется при обращении к защищённым API:

```http
Authorization: Bearer <access_token>
```

Внутренние маршруты взаимодействия сервисов также должны иметь соответствующую защиту доступа.

# Текущее состояние

Проект находится в активной разработке. Реализованы базовая инфраструктура, пользовательский профиль и его LLM-анализ, обработка резюме, Go Parser для Habr Career, хранилища и запуск поиска.

Текущий этап — формирование единого поискового pipeline на основе пользовательских данных.

Ближайшие задачи:

1. Проверять вакансии отдельно для каждого заинтересованного пользователя.
2. Создать и сохранять связь `Vacancy ↔ User`.
3. Передавать отобранные вакансии на LLM-анализ.
4. Реализовать `VacancyFeatures`.
5. Реализовать `VacancyMatch`.
6. Настроить периодический поиск через Celery Beat.

Дальнейшее развитие включает улучшение качества анализа, подключение новых источников вакансий, тестирование полного pipeline, подготовку production-инфраструктуры и создание пользовательского интерфейса.
