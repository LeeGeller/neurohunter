# **Следующие шаги**

Сейчас основной этап разработки — **сторона Go: получение данных пользователей, поиск по `job_titles` и первичная фильтрация вакансий**.

## **1. Получение пользователей в Go**

Нужно реализовать `internal/users`.

Go должен получать только те данные, которые необходимы для поиска и первичной фильтрации:

```text
User
├── user_id
├── job_titles
└── hard_constraints
```

Предполагаемая структура:

```text
internal/
└── users/
    ├── client.go
    └── models.go
```

`client.go` должен отвечать за получение данных пользователей, а `models.go` — за структуры, которые используются внутри Go.

Не нужно передавать в Go весь `UserFeatures`: сложные характеристики пользователя потребуются позже, на этапе анализа и matching.

---

## **2. Получение и обработка `job_titles`**

После получения пользователей нужно собрать все `job_titles`.

Поток:

```text
Users
  ↓
job_titles
  ↓
объединение списков
  ↓
очистка
  ↓
удаление дубликатов
  ↓
уникальные поисковые запросы
```

Например:

```text
Python Backend Developer
Backend Developer
Python Developer
Python Backend Developer
```

должны превратиться в набор уникальных запросов.

После этого каждый уникальный `job_title` используется для отдельного поиска.

---

## **3. Поиск вакансий**

Для каждого уникального поискового запроса:

```text
job_title
   ↓
Go /search
   ↓
Habr
   ↓
Vacancy
```

При этом одна и та же вакансия может встретиться в результатах нескольких поисковых запросов, поэтому её необходимо сохранить только один раз.

---

## **4. Получение `hard_constraints`**

Вместе с пользователями Go должен получать их `hard_constraints`.

На этом этапе нас интересуют только ограничения, которые можно проверить по уже структурированным данным вакансии.

Например:

```text
зарплата
формат работы
местоположение
опыт
график
тип занятости
командировки
```

---

## **5. Первичный отбор вакансий в Go**

Нужно реализовать `internal/filtering`.

Предполагаемая структура:

```text
internal/
└── filtering/
    ├── primary.go
    └── models.go
```

Логика:

```text
Vacancy
   +
hard_constraints пользователя
   ↓
Primary Filter
   ↓
подходит / не подходит
```

Проверка должна выполняться обычной логикой Go, без LLM.

Например:

```text
Вакансия:
Удалённая работа
Зарплата от 180 000
Без командировок
```

и пользователь:

```text
Удалённая работа
Минимальная зарплата 150 000
Командировки запрещены
```

проходит первичный фильтр.

---

## **6. Определение пользователей, которым подходит вакансия**

Одна вакансия может пройти первичный фильтр сразу для нескольких пользователей.

Например:

```text
Vacancy
   ↓
Primary Filter
   ↓
User 1
User 4
User 9
```

На этом этапе мы только определяем потенциально подходящих пользователей.

Подробного matching здесь ещё нет.

---

## **7. Связь `Vacancy ↔ User`**

После первичной фильтрации нужно сохранить информацию о том, для каких пользователей вакансия прошла фильтр.

Пока эта связь в проекте не реализована.

Предполагаемый результат:

```text
Vacancy
├── User 1
├── User 4
└── User 9
```

Вариант хранения будет определён во время реализации.

---

## **8. Передача вакансий на дальнейший анализ**

После первичного фильтра вакансии, которые подходят хотя бы одному пользователю, передаются дальше:

```text
Habr
  ↓
Vacancy
  ↓
Primary Filtering
  ↓
Vacancy ↔ User
  ↓
MongoDB
  ↓
Celery
  ↓
LLM
  ↓
VacancyFeatures
```

Вакансии, которые не подходят ни одному пользователю, не должны проходить дорогой этап LLM-анализа.

---

## **9. Следующий после Go этап**

После завершения поиска и первичной фильтрации можно переходить к:

```text
Vacancy
    ↓
VacancyFeatures
    ↓
UserFeatures
+
ResumeFeatures
    ↓
Matching
    ↓
VacancyMatch
```

Именно после появления `Vacancy ↔ User` можно будет использовать эту связь для более детального анализа вакансии только относительно тех пользователей, для которых она уже прошла предварительный отбор.
